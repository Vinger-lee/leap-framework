# Scope and limits: what LEAP does not guarantee

This page states the boundaries of the framework explicitly, so an integration decision is not made
on an optimistic reading of the README. It lists what the runtime does own, what stays with the host
agent, and which claims would need evidence that does not exist yet.

## 1. What the runtime does own

- **State consistency.** Learner state, evidence stages, mastery estimates and review schedules are
  persisted, versioned and reproducible from the event log.
- **Transition authority.** Nothing advances without passing the State Guard, and a refused
  transition is a structured rejection, never a silent write.
- **Mastery estimation.** `mastery_probability` is computed server-side from submitted evidence by
  the configured estimator; the host cannot send it.
- **Review scheduling.** FSRS intervals and retrievability, per node and per card.
- **Delivery structure.** Domain grounding needs source locators, excerpts, linked claims, worked
  checks and limitations; a teaching package must pair canonical Markdown with its projection and
  carry the required sections before items can be registered.
- **Auditability.** Every state change is an event with a request id, and rejections are logged with
  their reason.

## 2. What stays with the host agent (and its LLM)

- **Subject-matter truth.** LEAP validates the *shape* of what you submit. It does not verify that a
  proof is valid, a derivation correct or a claim sourced. Structural acceptance is not a
  correctness proof, and the repository says so in its own gates.
- **Item quality.** Difficulty, ambiguity, boundary coverage and distractor quality are the host's
  responsibility; the runtime only records that an item was reviewed and registered.
- **Explanation quality and pedagogy in language.** The policy engine selects a strategy and an
  action; the words, examples and diagrams are generated by the host.
- **Open-answer judgement.** Free-text reasoning requires host semantic review. Rule scoring is
  refused for items registered with `assessor_scope=host_semantic_review`, and no runtime component
  produces the semantic score for you.
- **Knowledge-graph design.** Decomposition quality decides what every later guard and estimate is
  built on. `validate_knowledge_dag` checks structure (cycles, dangling edges, prerequisite order),
  not whether the decomposition is academically right.

## 3. Engineering limits of this release

- **Single machine, single learner (P0).** The MCP transport is stdio, `auth_enabled` is false, and
  there is no learner account system, multi-tenancy, permissions or content moderation. A
  school-facing deployment needs all of that and LEAP does not provide it.
- **One implementation per pluggable seam.** All six seams are wired, but the shipped defaults are a
  simplified BKT estimator, a weighted aggregator, the rule-based policy engine, `py-fsrs`, SQLite
  and a local artifact store. Alternatives are additive, not yet proven in production.
- **Operational footprint.** The host runs an MCP stdio process, a SQLite file and a YAML config.
  `python -m leap.doctor` checks those prerequisites, and the `quickstart` tool profile reduces the
  catalog an agent must navigate, but the process still has to be supervised like any other local
  service.
- **Cost of a teaching turn.** The coarse tutor API reduces the call count; it does not reduce the
  token cost of the content the host must author.

## 4. Claims that have no evidence yet

Stated plainly, because a framework should not borrow credibility from its architecture:

- **No controlled efficacy study.** There is no published comparison of learning outcomes with LEAP
  against a prompt-only baseline, and no claim in this repository should be read as one.
- **No field data at scale.** The examples and the curriculum recipe are synthetic or
  author-produced fixtures; they demonstrate that the workflow runs, not that it teaches better.
- **No third-party curriculum validation.** Bundled subject notes and the Math I chapter are
  verified structurally and against their cited sources by the repository's own scripts; that is an
  internal check, not independent review.
- **No proof that a specific host model uses the surface well.** Tool-selection reliability depends
  on the host agent. The facade and `next_call` guidance make the correct sequence explicit; they do
  not make a weak tool-user strong.

## 5. How to read a claim in this repository

Two questions separate an implementation claim from an efficacy claim:

1. Which command or test would fail if the claim were false? (The README links the verifiers and CI
   runs them.)
2. Does the claim describe behaviour of the runtime, or quality of what a model produced with it?

If a sentence cannot answer the first question, treat it as design intent. If it slips into the
second, it is out of scope for this framework - and it should be corrected here rather than repeated
in a marketing page.

> [!note]- Reading and verification sequence: LEAP scope limits guarantees evidence
> Start with the definitions and scope in this note. Follow each prerequisite link before applying the workflow.
> Work through a concrete input and retain intermediate results; compare the output with the applicable contract or definition.
> For a failure, preserve the original input, the exact rejection reason and the corrected next action. A successful transport call is evidence of execution, not of domain correctness or learning.
> After the worked case, change one condition and state which conclusion still follows. Store the result as a timestamped observation rather than promoting evidence locally.
